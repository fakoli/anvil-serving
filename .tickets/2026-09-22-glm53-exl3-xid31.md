# GLM-5.3 EXL3 GPU illegal access during concurrent serving; engine failure exits with code 0

Status: open; incident diagnosed to GPU/runtime failure, faulting kernel unproven.

Tracking: https://github.com/fakoli/anvil-serving/issues/562

## Impact and observed sequence

The model endpoint stopped serving Pi requests. The gateway remained
available and returned errors for affected requests.
The first observed GPU error was at **2026-09-23 01:25:49 UTC** (September 22
18:25:49 Pacific). Only one Xid event appears in the retained current-boot kernel
journal; this is not proof of no older failures.

1. NVIDIA reports **Xid 31**, `FAULT_PDE ACCESS_TYPE_VIRT_READ`.
2. The rank-1 NCCL watchdog reports `CUDA error: an illegal memory access was
   encountered`; the worker dies and the executor begins shutdown.
3. About nine seconds later, the engine raises `EngineDeadError`; in-flight
   gateway calls fail with HTTP 500, followed by HTTP 503 on subsequent calls.
4. The container exits at 01:25:59 UTC with **exit code 0**, `OOMKilled=false`,
   restart count 0, and Docker restart policy `no`.
5. The launch unit remains `active (exited)`: it is `Type=oneshot` with
   `RemainAfterExit=yes`. Its `Restart=on-failure` supervises the launcher, not
   the subsequently detached engine. This explains the persistent outage,
   independently of the initial GPU fault.

## Exact runtime and workload envelope

- Model artifact: `brandonmusic/GLM-5.3-Flash-tr3-4bpw`, revision
  `a5fee929cf4888b1824323e33e8a19b60129e025`.
- Image: `verdictai/glm53-flash-exl3-k4:r19-sm120-tp2-ep2-dcp2-v84-language-only`,
  digest `sha256:0f1cdcc8891f1cc3a444121eb61d366289a1cbba285f0892dcbb24bc94961692`.
- Two RTX PRO 6000 Blackwell Max-Q GPUs; driver 595.91.07; TP2/EP2/DCP2;
  EXL3 routed experts; FP8 DS-MLA KV; prefix caching enabled; speculation disabled;
  configured context 327,680, maximum sequences 4, batched-token budget 2,048.
- vLLM reports `0.1.dev20111+g7f1e92bec.d20260827`; the embedded Git HEAD is
  `6dc2f516688fe6f84c6994dcd20fddf296853a6c`. Treat the image digest and inspected
  file hashes as stronger identity than the package version string alone.
- The fatal scheduler dump has two requests: a new 31,963-token prompt assigned
  2,047 prefill tokens, and an existing request at 174,956 computed tokens assigned
  one decode token. The new request has no multimodal features; no encoder work
  is scheduled. Pi parent/delegate request IDs correlate with the gateway errors.
- Reported KV utilization is 15.2%, prefix-cache hit rate 95.3%, zero waiting
  requests. Low KV utilization does not measure overall VRAM headroom.
- No contemporaneous host OOM was found. After exit, neither GPU reports a compute
  process or allocated VRAM, but the other GPU repeatedly reports 100% utilization
  and about 90 W. This is an unresolved post-crash anomaly, not proof of a live
  workload or permission to reset it. Recovery action reports `None`; ECC is
  disabled, so unavailable ECC counters cannot establish hardware health.

## Root-cause assessment

Confirmed: a GPU illegal-access failure killed the serving runtime; the lifecycle
configuration did not recover it. NCCL is where the asynchronous error surfaced,
not proven to be the kernel that caused it. Neither prompt size, OOM, Pi itself,
nor defective hardware has been established as the trigger.

[Upstream image issue #3](https://github.com/brandonmmusic-max/glm-5.3-flash-exl3-4bpw/issues/3)
reports similar Xid 31/43 failures under concurrent chunked prefill and prefix-cache
churn, but uses MTP3, NVFP4 KV and another image variant. Its closed state does not
prove this pinned image is fixed. Related
[PR #535](https://github.com/local-inference-lab/vllm/pull/535) and
[PR #536](https://github.com/local-inference-lab/vllm/pull/536) concern cache-page
geometry and target recurrent checkpoints; they must not be applied blindly to
the non-speculative FP8 deployment.

Read-only inspection of the exact stopped container establishes:

- `vllm/v1/attention/backends/utils.py:1005` retains the reported Triton gather:
  its mask is `offsets < NUM_STATE_BLOCKS`, without a row-width bound for
  `start_idx + offsets`. This is a concrete bounds-checking lead; incident reachability
  is unproven because the failing indices and row width were not captured.
- `vllm/v1/core/sched/scheduler.py:362` already contains intermediate-chunk and
  unaligned-resume guards. Six CPU-only checks against the extracted actual method
  pass the selected fragmented-chunk cases with speculation both off and on.
  Therefore “the old fragmented-chunk guard is entirely missing” is not supported.
  These checks are not a GPU reproducer or the complete upstream regression suite.

[NVIDIA's Xid catalog](https://docs.nvidia.com/deploy/xid-errors/analyzing-xid-catalog.html)
classifies Xid 31 as an MMU fault and recommends instrumented application debugging;
application, driver and hardware causes remain possible.

## Follow-up and acceptance

- Preserve the failed container and private crash evidence before recreation.
- Run a bounded synthetic reproduction in a separately declared managed recipe:
  match the FP8/non-speculative configuration and overlapping long decode/new
  chunked prefill; warm/churn the cache. Capture synchronous kernel attribution
  or Compute Sanitizer evidence before declaring the gather or APC causal.
- Compare the same workload with APC disabled only as an explicit experimental
  control. Do not change the selected route, promote a replacement, or replay
  private user prompts implicitly. A successful restart alone is not a fix.
- If the state-table lookup is reached out of bounds, repair the shared owner
  contract with a deterministic failing regression and a pinned derived image;
  do not silently clamp bad state indices and serve corrupted content.
- Make supervision reflect engine death and preserve fatal reason/exit evidence.
  Any approved bounded restart policy must handle fatal engine exits returning 0,
  retain owner control, and avoid a restart loop. Verify with a synthetic exiting
  service rather than deliberately crashing production GPUs.
- Expose exit code, OOM flag, finish time and restart policy through managed recipe
  diagnostics. Installed status lacked these fields; narrow read-only Docker state
  inspection was needed. Bounded source inspection is already tracked separately
  in `2026-09-19-recipe-runtime-source-diagnostics.md`.

During the initial diagnosis, no runtime configuration, model lifecycle, GPU reset,
driver change, route change, or production replay was performed. Raw logs, source
copies, request/session identifiers, GPU identifiers and operator paths remain
outside Git. This ticket intentionally contains only sanitized incident facts.

## Available fixes checked on September 22

The publisher's Docker Hub tag inventory still has the August 28 v84 digest above
as its latest image. `language-only`, `dflash2`, and the corresponding `current`
tag resolve to that same digest; switching these tags would not install a fix.
The publisher repository has no newer GitHub release. Issue #3 was closed without
a linked fix commit or a replacement image in its visible discussion.

- [Runtime PR #718](https://github.com/local-inference-lab/vllm/pull/718), merged
  September 11, fixes Mamba recurrent-state cleanup stopping at null gaps. It is
  relevant to cache lifetime, but its author explicitly limits the claim to cleanup,
  not corruption repair or production qualification.
- [Runtime PR #619](https://github.com/local-inference-lab/vllm/pull/619), merged
  September 11, fixes CUDA-stream/temporary-storage lifetime for an optional KDA
  gate-overlap path. Applicability to the deployed path has not been established.
- [Runtime PR #676](https://github.com/local-inference-lab/vllm/pull/676), merged
  September 11, repairs partial-page prefix reuse. It is not presented as an Xid fix.
- The alternate [SGLang SM120 recipe](https://github.com/ormandj/sglang-glm53-flash-sm120/releases/tag/v0.4.3)
  remains at v0.4.3, released September 11. It uses a different weight/runtime
  composition and is not an EXL3 image update.

Decision: retain these as patch/qualification leads. No verified drop-in fix was
found for this exact pinned configuration. The subsequent recovery used the same
configuration under explicit user authorization; it does not establish a repair
for the crash. This bounded search is not an exhaustive recipe survey.

## Recovery verification — 2026-09-23 UTC

The user authorized restarting the same recipe to unblock Pi work. The existing
service owner executed managed recipe unload/load after previews and preservation
of the failed container's logs, identity, source excerpts and exit evidence.
The original container was replaced; retained evidence remains outside Git.

- Health returned HTTP 200 at approximately 02:17:23 UTC. Exact image and model
  identities matched the incident configuration. Recipe and router file hashes
  were unchanged. No new runtime patch, GPU reset, driver change or catalog edit
  was applied.
- Direct recovery preflight passed all five selected check groups: text smoke,
  structured JSON, two tool calls, streaming tool call and tool-result continuation.
  Checks requested Max reasoning with 8,192 reasoning-headroom and 2,048 visible
  tokens. This is a bounded functional smoke, not long-context qualification.
- A fresh ephemeral Pi CLI run through the authenticated gateway invoked the
  read tool, consumed its result and returned the exact file canary in 13.11 s.
  Extensions and repository context were disabled; the run did not alter an
  existing user session. It establishes this client/protocol path, not all Pi
  extensions or the browser UI.
- Both GPUs resumed model allocation and the anomalous 100% idle utilization
  reading cleared during startup. No new Xid was observed through these checks.

Two harness corrections are retained privately: the initial preflight command
combined mutually exclusive reasoning options and was rejected before inference;
the first Pi subprocess inherited diagnostic stdin, so the clean final run used
DEVNULL. Neither is recorded as a model failure.

Status remains **open: service recovered, crash root cause unresolved**. The
long-lived/concurrent/cache-churn workload was not reproduced. Successful smoke
checks do not establish that the intermittent fault cannot recur.
