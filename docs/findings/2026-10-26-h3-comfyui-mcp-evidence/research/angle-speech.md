# Speech-driven video for a three-host podcast — stage 1 evidence

Research/access date: **2026-10-26**, source collection 13:22–13:34 UTC; report drafted afterward. Origin: Windows host local-windows-user. Research agent: /root/podcast_speech_research, inherited parent model (exact engine identifier not exposed). **Source research only; not local qualification.** Stage 2 must freshly verify decisive claims, and stage 3 must challenge the synthesis. This agent downloaded no weights, installed nothing, ran no inference, changed no services, and wrote only this file and its provenance companion.

## Answer

The best first experiment for this requirement is **recorded audio master → fixed character/studio assets → speaker close-ups and cutaways**, using **LatentSync 1.6 on existing/generated source clips** when preserving the shot matters, and **LeapTalk on a fixed portrait** when producing substantial speaking footage quickly matters. This is an engineering inference from the sources below, not a demonstrated complete podcast pipeline. Retain each original recording and the final mixed master; supply clean, time-aligned per-speaker audio copies for conditioning, and attach the untouched master after the visual edit. Mouth editors and whole-frame generators solve different problems: the former preserve most of an established shot; the latter can invent gestures but introduce more opportunities for identity, clothing, set and camera drift.

**No reviewed source demonstrates a production-ready, fully local, three-person, long-form studio podcast on one 32 GB RTX 5090 with stable identities across arbitrary cuts.** Native ComfyUI InfiniteTalk has one- or two-speaker modes. AnyTalker explicitly exposes three-position audio binding, but its released 14B multi-person recipe requires at least 80 GB VRAM; the 1.3B release is an earlier training stage with weaker synchronization. The promising current discovery is **LeapTalk (2026)**: an author-linked community integration has original Windows RTX 5090 measurements through ComfyUI, including 96.5 seconds of output, but it supports one portrait/speaker per job, and its Windows-native runtime does not support WSL2 in that release. The proposed close-up workflow avoids depending on an unproved simultaneous three-host generator.

## Baseline and decision boundary

The parent supplied: one RTX 5090, **32,607 MiB = 31.843 GiB**; Windows RAM 96 GB; WSL allowance 72 GiB RAM + 8 GiB swap; typical container 64 GiB RAM / 72 GiB RAM+swap. H3 base peak 31,402 MiB leaves **1,205 MiB**; guided upscale 30,106 MiB leaves **2,501 MiB**. These are arithmetic consequences of supplied measurements, not measurements made here. Run companion stages sequentially after H3 releases its GPU allocations; even a small persistent worker conflicts with that budget. Windows process RSS, Windows commit charge, Linux/container RAM, allocator-reserved CUDA bytes and whole-card NVML usage are different quantities.

A disk-size total is not a residency estimate. Unknown activations, attention/VAE workspaces, host staging and offload are left **unknown** below. RAM limits must be checked in the process/container actually used; 96 GB installed Windows RAM is not 96 GB available to a 64 GiB container.

## Five candidate paths

### 1. LatentSync 1.6 mouth editing; MuseTalk 1.5 as the faster baseline — worth testing

**Job:** apply supplied speech to a source face video, retaining its camera/body/set motion. This is the strongest architectural match for identity/style continuity when H3 or real footage already establishes the shot. No per-host training is required for ordinary inference. Source performance controls body gestures; these tools do not infer a complete new studio performance from audio.

The official [LatentSync README](https://github.com/bytedance/LatentSync/tree/a229c3948406bc2cf6eaf4873e662e70c6a04746) dates 1.6 to June 11, 2025 and states minimum inference VRAM **18 GB**, versus 8 GB for 1.5. Its [1.6 model card](https://huggingface.co/ByteDance/LatentSync-1.6/tree/c42c7e6c8e9c213626389fa7d9a3c444b8536353) specifies 512×512 training; the preceding 1.5 release had blurry teeth/lips. These are publisher requirements, not measured 5090 peaks.

**Three-person limitation:** the original [face detector](https://github.com/bytedance/LatentSync/blob/a229c3948406bc2cf6eaf4873e662e70c6a04746/latentsync/utils/face_detector.py) selects the largest eligible face. A group frame is therefore not a reliable three-track interface. Process a one-host shot, or explicitly crop/track each face and composite patches back. The latter is proposed pipeline work, not a verified built-in three-person recipe. The [pipeline](https://github.com/bytedance/LatentSync/blob/a229c3948406bc2cf6eaf4873e662e70c6a04746/latentsync/pipelines/lipsync_pipeline.py) reads frames and accumulates results for the clip; temporal inference blocks do not make the entire pipeline constant-memory. It can ping-pong a short source video to match longer audio, which risks conspicuous repeated body motion.

**ComfyUI:** [ShmuelRonen/ComfyUI-LatentSyncWrapper](https://github.com/ShmuelRonen/ComfyUI-LatentSyncWrapper) advertises Windows/WSL2, frontal visible faces, 25 fps and no anime/cartoon support. Its README still calls the official checkpoint private, contradicted by current HF API gated=false and accessible metadata. It also mixes a 20 GB training claim into its performance text. Prefer original requirements and inspect the wrapper version, rather than copying these claims. [Upstream issue 355](https://github.com/bytedance/LatentSync/issues/355), opened January 22, 2026 and still open when read, reports inability to run on a 5090; the existence of 32 GB does not settle runtime compatibility. [Issue 365](https://github.com/bytedance/LatentSync/issues/365), July 3, 2026, is an unmerged first-hand TensorRT-RTX/5070 Ti optimization report, not current upstream support.

**MuseTalk baseline:** [official README](https://github.com/TMElyralab/MuseTalk/tree/0a89dec45a0192b824e3cf4daf96c239440c5ed8) provides reusable avatar preparation and audio-file inference, 256×256 face patches, and 30+ fps on a V100. It reports a Windows 3050 Ti 4 GB test taking about five minutes for eight seconds, an existence proof at that precision/configuration, not a 5090 speed prediction. Its limitations include mustache/lip detail loss and jitter. The old torch 2.0.1/CUDA 11.8 recipe needs a Blackwell-compatible stack; [50-series issue 334](https://github.com/TMElyralab/MuseTalk/issues/334) documents dependency work and later user success, not a clean universal install. Training is optional and much heavier than inference.

**Disk:** LatentSync 1.6 U-Net 5,072,222,488 bytes + Whisper tiny 75,572,083 + SD VAE safetensors 334,643,276 = **5.482 GB / 5.106 GiB**, excluding face-detector/landmark assets and nonessential evaluation/training weights. The 1.6 HF archive is larger because it includes those extras. MuseTalk's own 1.5 U-Net alone is **3,400,074,924 bytes / 3.167 GiB**; VAE, Whisper, face parser and detector are additional. Exact full inference peak host RAM and 5090 VRAM are unknown for both.

**Licensing:** LatentSync code Apache-2.0; its 1.6 weight card says **openrail++**, not Apache. Its original pipeline uses InsightFace: [upstream license text](https://github.com/deepinsight/insightface#license) limits provided pretrained models to non-commercial research. Personal creative use is not automatically synonymous with research. MuseTalk code is MIT and authors allow their trained models for any purpose, but component licenses still apply. Do not confuse code and weight licenses.

### 2. LeapTalk 1-step streaming portrait + recorded speech — strongest exact-5090 discovery; worth testing

Original [project](https://github.com/zhangrongxiang/LeapTalk/tree/54dbd35d75ff69dc4f15f1855fd3bad10dad8a23), [paper v1](https://arxiv.org/html/2608.00079v1) dated July 29, 2026, and [weights](https://huggingface.co/z-rx/leaptalk/tree/b33b788fd1c9b3df11627e00c6a0415272d829dc). It anchors each chunk to the same portrait rather than relying solely on previously generated frames. No user-specific finetuning is required. It produces a single talking head; the released integration crops to 512×512 and is not a multi-host studio compositor or a gesture/pose controller.

The original repo links [ComfyUI-LeapTalk](https://github.com/hiroki-abe-58/ComfyUI-LeapTalk/tree/041d7a7ec979489619a446478157055383d20532). Its [setup](https://github.com/hiroki-abe-58/ComfyUI-LeapTalk/blob/041d7a7ec979489619a446478157055383d20532/docs/SETUP.md) pins upstream 5d8fef8dac3d1c9d3b3d5d9cceb6c76acc81e2c1, the above LoRA, FlashHead Model_Pro revision 59119b6c681230c3eeee157e224ae1941746711e, and wav2vec2 revision 22aad52d435eb6dbaf354bdad9b0da84ce7d6156. The tested stack is Windows 11 native, Python 3.12.13, torch 2.7.1+cu128, SDPA, no FlashAttention/SageAttention/torch.compile. **WSL2 runtimes are explicitly unsupported in this integration release.** Linux real-weight runs are untested.

The maintainer's [October 3 benchmark](https://github.com/hiroki-abe-58/ComfyUI-LeapTalk/blob/041d7a7ec979489619a446478157055383d20532/docs/BENCHMARKS.md) is first-hand external evidence: RTX 5090 32 GB, 64 GB Windows RAM, two synthetic portraits/English voices. A 96.5-second clip took **70.6 s queue-to-done** one-shot; peak **8.1 GiB allocated / 11.1 GiB reserved CUDA**, about **14.5 GB whole GPU** including the desktop. Process-tree RSS was about 5.1 GiB for a direct run; observed Windows commit addition was about 16.5 GiB. Warm persistent jobs were faster, but numerous attempts were refused/stopped by the memory guard under high background commit; warm timing medians exclude unsuccessful runs. **Use the one-shot result as the initial planning baseline.**

A separate [raw end-to-end artifact](https://github.com/hiroki-abe-58/ComfyUI-LeapTalk/blob/041d7a7ec979489619a446478157055383d20532/docs/results/gpu_e2e_report.json) corroborates 8,681,316,352 allocated and 11,874,074,624 reserved bytes and records strict LoRA/audio-projection application. Reference checks found identical pre-encoding frames for 234/234 and 850/850 frames against the official script. This proves implementation parity for those inputs, not human quality or recorded co-host performance.

**Chunk/seam/audio:** 33-frame window, five overlapping frames, **28 new frames/chunk at 25 fps**; original audio is handed off and muxed as AAC while a separate 16 kHz mono copy drives the model. AAC is not sample-identical preservation. Source review found small measured boundary differences; no human listening test was performed by the wrapper author. Audio guidance 2.0 produced oversharpened/discolored lips in that test; default 1.0 is the sensible first trial. Maximum real-weight tested duration is 96.5 seconds; an allowed 1,800-second configuration is not evidence of tested 30-minute quality.

**Disk:** selected Lite recipe files total **6,793,607,056 bytes = 6.794 GB / 6.327 GiB**; optional Wan VAE adds 507,609,880 bytes, totaling **6.800 GiB**. This uses FlashHead **Model_Pro + LeapTalk TAEHV**, not FlashHead Model_Lite/LTX VAE. [Component notice](https://github.com/hiroki-abe-58/ComfyUI-LeapTalk/blob/041d7a7ec979489619a446478157055383d20532/docs/LICENSING.md): LeapTalk code/weights, FlashHead Pro and Wan VAE Apache-2.0; TAEHV MIT notice retained. FlashHead's overall HF tag is other because its distinct Lite/LTX component has Open-RAIL-M restrictions; that is not the decoder this LeapTalk recipe uses.

### 3. InfiniteTalk sparse-frame V2V, or masked two-speaker ComfyUI — worth testing when gestures matter

Original [release/readme](https://github.com/MeiGen-AI/InfiniteTalk/tree/50aa0a94184315407a991ae804d9b58d6d311ba8), August 19, 2025. It conditions on a source video or still and supplied audio, and can change head, body and expression along with lips. This offers more expressive dubbing but less exact adherence to source motion. Source video is the stronger anchor for an established studio shot. Native [ComfyUI implementation](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy_extras/nodes_wan.py) exposes single_speaker/two_speakers with masks, confirmed directly in code; it does not expose three independent audio streams.

The [current official template](https://github.com/Comfy-Org/workflow_templates/blob/main/templates/video_wan2_1_infinitetalk.json) contains base generation plus extension groups, two audio loaders/masks and a 25 fps save path. It lists a scaled FP8 Wan I2V base, FP8 UMT5, InfiniteTalk FP16 patch, audio encoder, VAE and distillation LoRA. **Do not combine its repackaged patch with a different author's patch simply because the filenames look alike.** The current template's disk total for one multi-speaker variant is **29.686 GB / 27.647 GiB** (exact metadata below); this is not its VRAM requirement. Native source CLI also offers FP8/INT8 and zero persistent DiT parameters for offloading. Host RAM/peak workspace for this exact Comfy recipe is unmeasured in reviewed sources.

The [paper v1](https://arxiv.org/html/2508.14033v1), August 19, 2025, uses 81-frame chunks and nine prior frames, producing 72 new frames/chunk. The README says source camera paths are approximate; SDEdit tightens control but introduces color shift. Still-driven output is good for about one minute, then color drift becomes more pronounced. A moving/zooming still converted into video is an author-suggested workaround, not proof of a perfectly stable long podcast. The CLI defaults to a 1,000-frame / 40-second cap unless changed.

**Contrary evidence:** [original issue 210](https://github.com/MeiGen-AI/InfiniteTalk/issues/210), July 1 with September 15 follow-up, reports 40 minutes for 10 seconds on a 4090 with full offload/no quant or LoRA, and another user's roughly 15 minutes with FusionX/TeaCache. Not a current 5090 benchmark. [WanVideoWrapper issue 1308](https://github.com/kijai/ComfyUI-WanVideoWrapper/issues/1308), September 2025, reports a 15-minute input accumulating VRAM until OOM; it was closed September 30, but the thread does not establish which present revision/recipe resolves every long-job issue. [LightX2V's current 5090 multi config](https://github.com/ModelTC/LightX2V/blob/main/configs/infinitetalk/5090/infinitetalk_mutli_distilled.json) specifies 720p, four steps, 300-second target, FP8-SGL and block offload. That is a hardware-targeted configuration, **not a measured 300-second success**.

**License:** original models Apache-2.0; native Comfy repackaged cards Apache-2.0, separate wav2vec conversion card MIT. No specific host finetuning is necessary.

### 4. AnyTalker 1.3B / 14B — genuine three-person interface; 1.3B exploratory, 14B skip on this GPU

Original [README at e5490b6](https://github.com/HKUST-C4G/AnyTalker/tree/e5490b60dc6add439ff5ecec5bd7559606a78d53), weights first November 28, 2025; 14B multi-person checkpoint April 15, 2026. It binds audio left-to-right, explicitly including a middle and third person, accepts an arbitrary audio list, and provides pad mode for already aligned tracks. [Input/driver source](https://github.com/HKUST-C4G/AnyTalker/blob/e5490b60dc6add439ff5ecec5bd7559606a78d53/generate_a2v_batch_multiID.py) determines frame count from audio; this is not demonstrated constant-memory long-form streaming. Full-frame generation can add interactions and listening behavior, rather than preserve H3's source pixels.

**Release distinction matters:** the public 1.3B checkpoint is **stage 1, trained on single-person data**, although the repo shows two-person generation from it. The newer 14B multi-person checkpoint is explicitly documented to need **at least 80 GB VRAM with FP16 enabled**. Do not describe the paper's 14B interactivity results as quality delivered by the smaller released stage. The [paper v1](https://arxiv.org/html/2511.23475v1) reports generalization beyond two identities, but its quantified InteractiveEyes evaluation is two-person, about ten seconds per clip, 20 held-out examples. The three-person behavior is qualitative, not a 32 GB long-form benchmark.

**Disk:** the 1.3B checkpoint is **7.603 GB**; shared T5/CLIP/VAE and wav2vec safetensors bring selected weights to **24.622 GB / 22.931 GiB**, excluding an optional separately downloaded base DiT and detector assets. The 14B checkpoint alone is **83.952 GB**; corresponding selected components total **100.972 GB / 94.037 GiB**. These large serialized files are not proof of runtime residency, but indiscriminately downloading the entire model repository would fetch both variants. Peak RAM/VRAM for the 1.3B, three-host workload is **unknown**. Source installation pins torch 2.6/cu126 and FlashAttention; no exact 5090 evidence was found, so Blackwell runtime adaptation remains unqualified.

**License:** original models/code Apache-2.0; InsightFace pretrained detector terms remain separate. No per-host training is required for the released inference path; training an improved personalized three-host model was not researched as a practical first step.

### 5. SoulX-LiveAct — conditional motion/long-form lead with exact-5090 evidence and unresolved code license

Original [README at ac8579b](https://github.com/Soul-AILab/SoulX-LiveAct/tree/ac8579b907756f228e975922a5159765c93c6a34), released March 16, 2026, added consumer offload March 18 and FP4 May 27. The authors report **6 generated fps on one RTX 5090**, using FP8 KV and block/CPU offload. It provides timed action/emotion prompts, e.g. the original [edit JSON](https://github.com/Soul-AILab/SoulX-LiveAct/blob/ac8579b907756f228e975922a5159765c93c6a34/examples/example_edit.json). This offers control absent from mouth-only editing, but does not establish three-person independent voice binding. Hour-scale memory/continuity is the paper's claim, not a locally verified episode.

The [unofficial RTX5090 fork](https://github.com/5461gpt/SoulX-LiveAct-RTX5090/tree/917fc4599d5970332b6866be9ac19cbce9d0b6fa) links a complete NVFP4 checkpoint and WSL2 recipes. Its [original benchmark](https://github.com/5461gpt/SoulX-LiveAct-RTX5090/blob/917fc4599d5970332b6866be9ac19cbce9d0b6fa/docs/FP4_PREQUANTIZED_BENCHMARK.md) is narrowly specified: **3-second input, 256×416, 24 fps, seed 42, CPU T5, FP8 KV, CUDA12.8/torch2.8.0+cu128**. Peak allocated VRAM **20.72 GiB**, with [raw warm artifact](https://github.com/5461gpt/SoulX-LiveAct-RTX5090/blob/917fc4599d5970332b6866be9ac19cbce9d0b6fa/artifacts/benchmarks/prequant_warm.json) reserved 21,356 MiB. A warmed final block generated 1.333 seconds in 5.07 seconds; the full cached process still took 774.50 seconds, including CPU T5/initialization. **Do not call that real time.**

The later recommended GUI profile is a different **256×416, 3-step, 15 fps** setting: first chunk about 2.11 seconds and reported steady aggregate RTF about 1.039, with about 60-second warmup. Its [guide](https://github.com/5461gpt/SoulX-LiveAct-RTX5090/blob/917fc4599d5970332b6866be9ac19cbce9d0b6fa/docs/RTX5090_REPRODUCTION_GUIDE_ZH-TW.md) recommends at least 64 GB RAM and 80 GiB free disk, and explicitly leaves a clean second-5090-machine reproduction undone. The earlier measured 20.72 GiB is not a measured peak for every later GUI/long-form setting.

**Disk/licensing:** native weight files + chosen audio encoder total approximately **54.791 GB / 51.028 GiB**. Quantized shards add **11.089 GB / 10.327 GiB**; the fork still uses original auxiliary components and recommends keeping original weights. No complete host-residency measurement was located. Original and quantized model metadata say Apache-2.0, but the fork's [NOTICE](https://github.com/5461gpt/SoulX-LiveAct-RTX5090/blob/917fc4599d5970332b6866be9ac19cbce9d0b6fa/NOTICE.md) says the upstream code had no license file and model metadata does not license the source tree. **Treat this as a research watch item until source-code rights and exact memory fit are resolved.**

## Current alternatives retained rather than overlooked

- **LongCat-Video-Avatar 1.5**: [original repo](https://github.com/meituan-longcat/LongCat-Video/tree/6b3f4b8582a8bc3f20f795735f5383716c4ba794), released May21 2026, is the successor now linked by InfiniteTalk/MultiTalk. Whisper-large-v3, mandatory distillation, optional INT8, 480p/720p, continuation, and two-audio para/add modes. Reference-index/mask-range knobs trade repeated actions against artifacts. MIT weights. Selected INT8 DiT files alone **15.880 GB/14.790 GiB**; DiT+DMD+one FP16 Whisper+separator+T5+VAE approximately **44.789 GB/41.713 GiB on disk**. The independent run above exceeded this GPU at 46,827 MiB even with an INT8 path. Quantized/community offload may change fit, but native32GB qualification is unproved. It is an expressive-quality comparison candidate, not an assumed fit; three independent audio streams are not in the documented recipe.
- **EchoMimicV3-Flash**: [author README](https://github.com/antgroup/echomimic_v3), released January22 2026, advertises 12G VRAM, whereas the independent default768-area run above used33,726MiB. Both can be true for different paths. The [original community Comfy wrapper](https://github.com/smthemex/ComfyUI_EchoMimic) claims 768×512/6.5G with block offload and new audio/transformer, and advises lowering partial_video_length. Tested GPU/model/host-memory scope for those minimum claims is incomplete; no exact5090 match found. Apache2 models; single-human animation, optional motion controls depending version. Worth a later quality/memory comparison, not rejected solely by the large default run.
- **FlashHead Lite/Pro**: [authors](https://github.com/Soul-AILab/SoulX-FlashHead) claim Lite96fps or three concurrent portrait streams on one4090; Pro10.8fps4090,25+fps on **two**5090s. Three concurrent independent portraits is not a coherent three-person studio frame. Its [HF component-license correction](https://huggingface.co/Soul-AILab/SoulX-FlashHead-1_3B) distinguishes Apache Pro/Wan from Open-RAIL-M Lite/LTX. LeapTalk supplies a newer derivative with closer hardware evidence.
- **Lip Forcing**: [original code](https://github.com/cvlab-kaist/LipForcing), 14B released July7 2026; constant-memory V2V requires about37GB on H200 with precomputed text embeddings,50GB with runtimeT5. The celebrated1.3B student is still unchecked in the release checklist/no released weights when read. A sub-millisecond paper time-to-first-frame is not a full application first-response measurement. Apache2; **skip released14B on32GB** without a separately evidenced quant/offload implementation.
- **TalkVerse-5B**: [original repo](https://github.com/snap-research/TalkVerse), releaseDecember31 2025, minute-long single-person baseline on Wan2.2-TI2V5B, with offload/T5CPU suggested for4090. Correct weight repo is [snap-research/talkverse-s2v-5b](https://huggingface.co/snap-research/talkverse-s2v-5b); a guessed snap-research/TalkVerse model lookup failed401 and was corrected. Code/data/weights use **Snap Non-Commercial License**. No exact5090 memory/time source located.
- **Wan2.2-S2V**: [author source](https://github.com/Wan-Video/Wan2.2), Aug26 2025; supplied audio and optional pose_video control. Original default14B single-GPU example requires80GB; lower-memory offload modes exist but are separate. S2V is distinct from Wan Animate, whose input performance video drives motion. ## Practical recipes to test later, not executed

1. **Source-clip continuity test:** use the same approved studio/character frame and source performance for each shot; generate a short H3 clip, unload H3, then process the visible speaker with LatentSync1.6 and MuseTalk1.5 under a Blackwell-compatible runtime. Compare identity outside the mouth, lips/teeth, beard/glasses/mic occlusion, and lip timing. For all-host wides, face crops/track identities/masks must be explicit; native largest-face selection is insufficient. Keep the original shot as a rollback artifact.
2. **Audio-first close-ups:** hold one approved portrait per host and run LeapTalk one-shot, one speaker at a time, maintaining the same clothing, crop, lighting and studio background assets. Use fixed shot boundaries around turns, insert listening/cutaway shots, preserve pauses and overlap in the master timeline. Independent head footage composited into a studio may look like a panel layout; it does not create natural shared gaze/contact geometry. Assess this visually before undertaking an episode.
3. **Motion dubbing:** when the source video supplies useful gestures, compare InfiniteTalk V2V to mouth editing with identical audio. For two hosts, test the native two-mask workflow and time-aligned para tracks. Do not relabel this as a three-host feature. Repeated extension groups/81-frame chunks require boundary review; hard scene cuts should deliberately reset shot context.
4. **Three-person exploratory still:** only after a short one/two-speaker baseline, try AnyTalker1.3B with three equal-duration zero-padded stems bound left/middle/right. Measure peakVRAM, hostRSS/commit, duration and failure rate, then compare lip timing/listener behavior. The 14B model is outside currentGPU's documented requirement.
5. **Recorded-master integrity:** conditioning copies may be mono16k/resampled/normalized by the model; final media should be synchronized back to the retained original master. Do not use a generator's AAC output as the archival master or count a waveform correlation below1 as exact preservation. A mixed recording without isolated tracks makes overlapping-speaker conditioning uncertain; diarization alone cannot recover separated overlapping speech. No real co-host recordings were supplied, so voice/face/accent/microphone/generalization claims remain untested.

**Smallest informative experiment, still not authorized to run here:** three approved10–20s recorded excerpts per host (clear speech, laughter/pauses, overlap), one frontal portrait and one source clip each; sequentially compare LatentSync1.6 vs MuseTalk1.5 vs LeapTalk. Record output timestamps, audio sample count/master checksum, visible identity consistency, blinded lip-sync preference, seam review, totalwalltime, cold/warm timings, peakNVML/allocated/reserved and process/containerRAM. Stop at this short acceptance set before rendering a full episode.
