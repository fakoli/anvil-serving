# Character identity, studio continuity and assembly — stage-1 research

Date: 2026-10-26. Researcher: /root/podcast_identity_research, Codex GPT-6-family agent; exact runtime model identifier was not exposed to this child. Source access: 2026-10-26 UTC. This is source-supported research for the parent’s fresh verification and adversarial review, not local qualification. No installation, model-weight download, inference, creative generation or service mutation was performed.

## Answer for this project

Use a canonical studio and three reusable character assets as the continuity authority, and keep the original recorded audio as the edit’s timebase. FLUX 3 Image Klein is the most useful newly released image candidate to test for reference-conditioned storyboard frames and, only if needed, separate per-host image LoRAs. A Blender studio gives exact prop counts, fan geometry, signs, camera positions and repeatable lighting. Rhubarb plus its maintained Blender integration provides a wholly local, conventional mouth-animation route for stylized characters. Kdenlive provides the long-form edit, camera cutting, titles and original audio assembly. This is a proposed architecture, inferred from the documented capabilities below; no source establishes an already automated, one-click, three-host, hour-long version of this exact workflow.

The MiniMax-H3 training ecosystem is real and materially more developed than “LoRA unsupported.” Fizgig documents pruned INT8 FL2VA/REF2VA training, image/video/audio datasets, training-only adapters, block selection, measured ablations and small-GPU operation. However, that is **capability evidence only for this US project**: the original MiniMax-H3 license explicitly excludes the United States, and the Cobijada derivative explicitly preserves the underlying terms. Personal noncommercial use does not remove that territorial exclusion. Do not schedule H3 training or generation from these findings under the stated no-separate-permission condition. [H3 license](https://huggingface.co/MiniMaxAI/MiniMax-H3/blob/main/LICENSE), [Cobijada card](https://huggingface.co/Winnougan/Cobijada_Minimax-H3_Hybrid_Pruned_ComfyUI).

Reference conditioning should be the first image experiment because the hosts already have recorded footage/stills and no identity LoRAs. Per-host training becomes worthwhile only when the reference baseline fails held-out angles/expressions consistently. Neither an identity LoRA nor a fixed seed is a geometric studio model. Multiple identity adapters in one global denoiser do not, by themselves, assign each identity to its correct chair; use explicit reference-to-subject instructions and layout, or render/composite the characters separately. This last statement is an engineering inference, supported by the multi-instance identity/layout failure modes and tradeoffs documented in ContextGen, not a measured result on this cast. [ContextGen paper, v2, 2025-12-09](https://arxiv.org/html/2510.11000v2).

## FLUX 3 identity-training recipe and memory distinction

The official [collection](https://huggingface.co/collections/black-forest-labs/flux-3-image-klein) separates Base, distilled, Comfy packaging and prompt upsampler. The pinned [Fizgig FLUX3 guide](https://github.com/shootthesound/Fizgig/blob/20331b14ae514013be8617d21e1cfa6fef592f9f/docs/FLUX3.md) provides Ultra Fast: rank/alpha 16, adaptive LR 1e-4–2e-4, 50 epochs, 0.25 MP, adamw8bit, EMA 0.98, save every epoch. It warns support is experimental and inherited presets need FLUX3 tuning. This is a starting experiment, not a cast-specific optimum.

Proposed dataset construction, not a publisher-validated cast recipe: make one folder per host; select sharp, nonduplicated frames from their real footage, include the real available front/three-quarter/profile views, expressions and lighting, and exclude motion blur/obstructions. Begin with approximately 20–40 diverse stills per host and reserve held-out source footage. Use one uncommon token per host, caption clothing/pose/background explicitly and keep a separate style specification; do not teach the person only against the same studio backdrop. Repeated adjacent video frames add little independent identity coverage. Do not synthesize imaginary rear/profile identities and silently treat them as recorded evidence. The 20-image size has a concrete creator precedent below, but the 20–40 range and split are proposed experimental choices.

The FLUX3 guide reports **RTX 5090**, rank-16, 1 MP training peaks: 12.7 GB BF16, 9.1 GB INT8, 6.2 GB NF4. It does not specify NVML versus allocator measurement, all environment versions or multi-reference training cost; those gaps prevent treating it as our qualification. Its files are about 11.1 GB each for Base/distilled transformer, 8.9 GB encoder and 0.3 GB VAE. Cache latents/text and unload the encoder for training; do not co-reside an unnecessary 9B prompt upsampler. Use prepared full scene captions or a separately run local prompt expansion stage, as the card permits. [FLUX3 guide](https://github.com/shootthesound/Fizgig/blob/20331b14ae514013be8617d21e1cfa6fef592f9f/docs/FLUX3.md), [card](https://huggingface.co/black-forest-labs/flux-3-image-klein).

Independent implementation evidence is narrower: [Hugging Face’s 2026-10-15 Diffusers report](https://huggingface.co/blog/flux-3) gives 20.72 GiB BF16 inference peak on H100 in one table and 23.8 GiB in its H100 end-to-end timing table; its NVIDIA RTX6000 NVFP4 arm is 15.3 GiB. The BFL card instead reports 31/26/25 GB on B200 BF16/FP8/NVFP4 with its reference code and upsampler off. These are different implementations/configurations, not interchangeable memory or timing guarantees. Multi-reference peaks on this 5090 remain unknown.

Parameter/state estimate, **calculation rather than measurement**: pinned [model source](https://github.com/shootthesound/Fizgig/blob/20331b14ae514013be8617d21e1cfa6fef592f9f/src/fizgig/flux3/model.py) has hidden 3072, MLP ratio 3, 15 modality blocks plus 28 joint blocks. Pinned [driver](https://github.com/shootthesound/Fizgig/blob/20331b14ae514013be8617d21e1cfa6fef592f9f/src/fizgig/flux3/driver.py) targets q/k/v, attention out and two MLP linears. Rank 16 across all 43 blocks gives 43 × 16 × 58,368 = **40,157,184** adapter parameters. At default FP32 adapter weights/gradients, two byte-per-parameter 8-bit optimizer state and FP32 EMA, storage is roughly 14P = **0.524 GiB**, excluding quantization scales, temporaries, frozen auxiliary adapters and activations. Some reference-only modules receive no gradients during pure T2I, so this is a conservative bookkeeping scenario, not an exact live-state count. The [shared adapter source](https://github.com/shootthesound/Fizgig/blob/20331b14ae514013be8617d21e1cfa6fef592f9f/src/fizgig/families/lora.py) defaults trainable parameters to FP32. Activation and workspace peaks are unknown; use the creator’s whole-run numbers only as external evidence and measure both GPU and process memory in a future authorized run.

## H3-specific support: real capability, excluded from current execution

H3 here means **MiniMaxAI/MiniMax-H3**, not any Hunyuan image/video model. Native [H3 card](https://huggingface.co/MiniMaxAI/MiniMax-H3) distinguishes FL2VA (zero/one/two endpoint images) and Ref2VA (up to nine images, three video clips, three audio clips, at most twelve files total; reference audio/video aggregate duration limits apply). Base output is 24 fps, 32 kHz stereo and 4–15 seconds, not one long podcast. Its Context-IR system is described as hosted; following the published reference prompting convention is the local alternative, not a claim that the complete hosted orchestration ships in the weights.

Fizgig’s current [CLI guide](https://github.com/shootthesound/Fizgig/blob/20331b14ae514013be8617d21e1cfa6fef592f9f/docs/CLI.md) documents a three-stage workflow: cache video-VAE latents, cache Qwen3-VL text, then train. It accepts the pruned INT8 ConvRot DiT used in ComfyUI (~21 GB), the ~15.7 GB NVFP4 text encoder, video VAE, optional audio VAE, optional Turbo preview LoRA, and a training-only assistant adapter. The reference DiT is the selected base for LoRAs intended for Ref2VA. The default current [family preset source](https://github.com/shootthesound/Fizgig/blob/20331b14ae514013be8617d21e1cfa6fef592f9f/src/fizgig/families/minimax.py) specifies rank/alpha 8, batch/accumulation 1, 50 epochs, seed 42, 0.25 MP, Automagic3 starting LR 1e-6, EMA 0.98, caption dropout 0.05 and 60% low-noise steps. The identity window is blocks 20–49; the token refiner and AdaLN are omitted by default. This is a reproducible candidate recipe, not a recommendation to execute in the US.

Training-only assistants matter on this guidance-distilled model. [Circlestone’s 2026-09-10 adapter](https://huggingface.co/circlestone-labs/MiniMax-H3-Image-Training-Adapter) is merged/fused during image training, omitted for inference, and explicitly should not be combined with guidance-preservation/CFG-augmented training. Fizgig currently prefers Circlestone for photos and variant-matched Ostris assistants for video-only runs. The claim that one Circlestone assistant serves both bases does **not** prove a learned person LoRA transfers unchanged between arbitrary FL, REF, hybrid, quantized and future checkpoints. Train/deploy on the same exact base and record its hash if this ever becomes licensed and authorized. The current Cobijada hybrid has a different late-AdaLN selection; no fetched source qualifies identity training against that exact revision.

For actual recorded movement, the [H3 guide](https://github.com/shootthesound/Fizgig/blob/20331b14ae514013be8617d21e1cfa6fef592f9f/docs/MINIMAX_H3.md) requires MP4 at exactly 24 fps; frame counts 5,22,39,56,73,90,107,124; dimensions divisible by 32; audio 32 kHz stereo or absent. Its 32 GB tier allows up to 56 frames at 0.5 MP, 73–90 at 0.5 MP, or 107–124 at 0.25 MP. It reports 22-frame training around seven times a still’s cost and 124 frames around 37 times. This is short-clip appearance/motion adaptation. Original voices need not be learned at all if the original soundtrack remains the master.

### H3 training feasibility is not established by inference

User-supplied baseline, not remeasured by this child: 32,607 MiB = **31.843 GiB** VRAM. Base inference peak 31,402 MiB = 30.666 GiB, leaving **1,205 MiB**; guided 2× upscale peak 30,106 MiB = 29.400 GiB, leaving **2,501 MiB**. Generator weights 19.53 GiB plus encoder 25.277 GiB sum to **44.807 GiB**, so sequential residency is essential. None of these inference peaks is a training budget.

Sizing calculation: in pinned [H3 model source](https://github.com/shootthesound/Fizgig/blob/20331b14ae514013be8617d21e1cfa6fef592f9f/src/fizgig/minimax/model.py), hidden=5376, attention width=56×128=7168, FFN=14336; [driver](https://github.com/shootthesound/Fizgig/blob/20331b14ae514013be8617d21e1cfa6fef592f9f/src/fizgig/minimax/driver.py) targets qkv/out/fc1/fc2. Rank 8 uses 8 × (26,880+12,544+34,048+19,712) = 745,472 parameters per main block. Active 30-block identity window: **22,364,160 P**. All 50 main-block adapters instantiated: **37,273,600 P**. Default FP32 weights take **85.31–142.19 MiB** across those counts; gradients and EMA can each add a comparable amount. The actual optimizer/dropout/backward-cut configuration decides which states exist.

[Automagic3 source](https://github.com/shootthesound/Fizgig/blob/20331b14ae514013be8617d21e1cfa6fef592f9f/src/fizgig/training/automagic3.py) stores sign history in packed bits plus factored row/column second moments. Its constructor uses H=8 although a nearby docstring still says default four: use the source, not that stale comment. With FP32 weights/gradients/EMA, H=8 and factored moments, adapter bookkeeping is approximately **0.28–0.47 GiB**, plus frozen assistant weights, quantization metadata and transient tensors. A conventional FP32 AdamW+EMA scenario is about 20P = **0.417–0.694 GiB**. These are storage estimates, not total training peaks. Cached embeddings and VAE outputs reduce co-residency; activations still scale with reference count, spatial resolution and clip tokens. The allocation for activations/workspaces and exact source RAM peak are **unknown for the custom hybrid**.

For scale, the original nominal 33B model alone is approximately 61.47 GiB at BF16. A conventional mixed-precision Adam training scheme at 18 bytes/parameter is about **553.21 GiB before activations**. This generic [HF memory anatomy](https://huggingface.co/docs/transformers/en/model_memory_anatomy) scenario is not the pruned LoRA recipe and not Fizgig’s rotating-window full-fine-tune method. It shows why inference, LoRA and ordinary full training cannot be conflated.

Fizgig’s [install/RAM guide](https://github.com/shootthesound/Fizgig/blob/20331b14ae514013be8617d21e1cfa6fef592f9f/docs/INSTALL.md) says ~32 GB system RAM for H3 caching/training and ~48 GB when previews park the ~21 GB base in RAM; Windows paging/commit spikes are called out. Those nominal values are below 64 GiB container RAM, but do not certify this environment’s 25.277 GiB encoder or custom model loader. [Docker’s resource documentation](https://docs.docker.com/engine/containers/resource_constraints/) distinguishes the memory hard limit from the combined memory-plus-swap limit. A larger Windows RAM allocation does not automatically enlarge either configured container allowance. Actual cgroup settings were not inventoried by this child.

There is exact contrary hardware evidence: [AI-Toolkit issue #1050, opened 2026-09-18, still open when fetched](https://github.com/ostris/ai-toolkit/issues/1050) reports Windows RTX 5090/32 GB, PyTorch 2.14+cu130, pruned INT8 Ref2VA: first-step hang with triton-windows, or about 40 GB BF16 staging/OOM without it, despite inference working. It also reports musubi trainer hangs. [Issue #1017, opened 2026-08-24, now closed](https://github.com/ostris/ai-toolkit/issues/1017) reports a 96 GB system exceeding 120 GB RAM during caching. These older AI-Toolkit reports do not disprove current Fizgig, but they decisively refute “same 5090 inference works, therefore any trainer fits/works.”

## H3 reference alternatives and their limits

Native references avoid person-specific training. **RefMods** from [Luisacaotica’s original repository](https://github.com/Luisacaotica/ComfyUI-MiniMaxH3Mod) cache/compress H3 VAE reference latents; they are not weight LoRAs. Upstream explicitly says API/schema evolving, small grids lose face detail, token copies add cost rather than information, speaker transfer failed in tests, and audiovisual synchronization is not enforced. Treat a “tiny file” as stored latent size, not tiny total attention/VRAM. Its model-free MSE refinement does not prove training through a full INT8 H3 checkpoint.

Fizgig’s separate [RefMod guide](https://github.com/shootthesound/Fizgig/blob/20331b14ae514013be8617d21e1cfa6fef592f9f/docs/REFMOD_HOWDOI.md) adds model-in-the-loop latent optimization: basic recipe eight photos at 1 MP, zero steps; lite sixteen photos at 0.5 MP, 200 steps, model frozen. This is optimization of reference data, not changing the foundation’s weights. It claims a same-seed held-out makeup condition scored 28 versus 21 likeness, and a variant-matched FL mod scored 65 versus 60 for a REF-tuned mod on FL. Dataset identity, frame counts/confidence intervals and full hardware recipe are missing: these are creator ablations, not independent benchmark wins. The examples strengthen the case for variant matching and testing unfamiliar views, not the claim of universal identity lock.

[Muse CharacterSheet H3](https://github.com/muse-collective-26/Muse-CharacterSheet-H3) is a concrete creator workflow: one H3 reference call creates a turnaround; five selected frames are composited into a sheet, with eight character/prop references plus a location reference and optional identity video. It is useful workflow evidence, not a proof that generated unseen views correctly recover a real host. It inherits H3’s license boundary. Its Enhanced path adds Qwen-Image 2.1 and DLSS; Standard avoids those additions. No installation or sample generation was attempted.

It would make isolated character layers easier, and Fizgig has specific LoRA training support. ## Studio accuracy, upscaling, and finishing checks

An incorrect sign, missing microphone, wrong fan, wrong sleeve or merged identity is a semantic/layout error. Upscaling is not a reliable repair stage: the [H3 guided upsampler](https://github.com/sandpies/ComfyUI-H3-Video-Upsampler) conditions a light two-step redraw on the original clip, with denoise0.1 selected to preserve it. Therefore it can make the original mistake sharper; increasing denoise can change identity/geometry rather than guarantee a correction. This is an inference from the documented guide-preservation mechanism. Its own README calls quality evidence an eyeballed blind comparison on H3 renders and warns generation from noise flickers every17frames. No systematic text/identity/prop-error repair benchmark was found.

Use deterministic layers for details whose correctness must be absolute: studio meshes/rigged fan rotation, fixed or tracked signs, lower thirds and readable labels. Inspect the accepted keyframe before animation, then inspect first/middle/last frames and transitions. For moving generated hosts behind a desk, verify matte edges and occlusion ordering.
